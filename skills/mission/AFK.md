# AFK mode

`/mission --afk` authorizes provisional judgment while the user is away. Complete the objective within its existing authorization and leave reviewable local work. Preserve what the user actually decided; label every answer you supply for them as provisional. A grilling design is a draft until the user reviews it.

## Start

1. Treat `--afk` and `--max-rounds N` as options; use the remaining argument as the objective or plan path. With none, recover the current objective, confirmed decisions, open questions, and relevant skills from this session. If there is no identifiable objective, ask for it before starting. Continue when the objective and the requested result are explicit in the ledger.
2. If given a plan path, use that file as the ledger and its stated deliverables. Otherwise create `ledger.md` and `result.md` under a writable task scratch directory; in OpenCode, `~/.local/state/opencode-mission/<date>-<topic>/` is the default when writable. Use an output path from the request when one exists. Put the objective, confirmed constraints, output paths, and a checkable **Done when** condition at the top.
3. Turn the work into `- [ ]` items with checkable conditions. For a grilling session, reconstruct its design tree from the conversation: confirmed answers stay confirmed, unanswered frontier questions become items, and dependent questions follow their prerequisites. Add a final item to audit the result against **Done when** and account for every branch. Continue when every known question and the final audit have an item.
4. In OpenCode only, write `.loop` at the working root as `{"mode":"afk","ledger":"<absolute path>","max_rounds":20}`. Use a requested `--max-rounds N` in place of 20. In other harnesses, continue the rounds in the active turn without a plugin file.

## Round

1. Read the ledger and the latest result. Pick the first unticked item whose prerequisites are met. Use the relevant skill's method; in a grilling session, advance its decision tree one frontier question at a time. Continue when the question and its checkable result are clear.
2. Find facts from files, tools, and sources. Dispatch one subagent with [BRIEF.md](BRIEF.md) when fact finding benefits from separate context; verify its findings yourself. For a choice the user has not made, select the best provisional answer from the evidence and their stated constraints. Record `Ruling: provisional — <decision> — <why> — <cost if wrong>` beside the affected work: in the result for design, or in the ledger for a plan with no result file. Include alternatives and conditions that would change the answer. Continue when facts and judgment are distinguishable.
3. Update the deliverable after each item. Add newly revealed questions as unticked ledger items before the final audit. Record `Needs user: <decision or approval>` beside the work for an action that requires their authority, then work on independent items. If documenting the needed decision completes a design item, tick it with that evidence. Use `BLOCKED: <item> — <what the user must provide>` in the ledger only when no meaningful part of the objective can advance. A lack of preference or an ambiguous design choice calls for a provisional ruling. Continue when the deliverable and ledger reflect the new evidence and questions.
4. Check the item's done condition yourself by inspecting the result and cited evidence or running its command. Tick it as `- [x] <item> — evidence: <check or source> → <observed result>`. Print `mission AFK: <ticked>/<total> ticked; next <item>`. In OpenCode, end this turn for idle continuation; in other harnesses, continue the next item.

## Authority and exit

Use this mode's provisional rulings in place of the grilling skill's wait for the user's answers. Keep the grilling skill's question tree and fact-finding discipline. State plainly in a design result that the user has not approved the provisional answers. Reversible local research, drafts, and implementation already authorized by the objective may continue. Secrets, irreversible or destructive work, pushes, merges, publishes, messages to other people, and other consequential external actions require the user's existing authorization; record `Needs user:` and continue independent work.

For the final audit item, inspect every deliverable against **Done when**, the full question tree or plan, every Ruling, and every `Needs user:` line. Remove tool-wrapper fragments such as `<content>` and `</content>` and check documents from start to end. For a design, mark the result `Draft for user review`, with sources, assumptions, alternatives, and remaining decisions. For implementation, run its done conditions and report the local changes and checks. Tick the audit only when the result is reviewable and every branch is accounted for. Then remove `.loop` if this run created it, notify the user when available, and report the output paths, ticked count, provisional Rulings, and remaining `Needs user:` items. In OpenCode, the plugin's round cap or no-progress stop leaves the ledger and partial result in place for review.
