# AFK mode

`/mission --afk` authorizes provisional judgment while the user is away. Follow the requested endpoint and existing authorization. Preserve confirmed decisions; answers supplied for the user remain provisional. A planning result is a draft until reviewed.

## Start

1. Parse `--afk` and optional `--max-rounds N`; the remaining argument is the objective or plan path. With none, recover the current objective, confirmed decisions, open questions, and relevant skills from the session. Ask only if no objective is identifiable. Extract the user features, constraints, non-goals, and source pointers using SKILL.md’s Input and conclusion rules. Preserve input briefs and record the requested result and **Done when** before starting. For an end-to-end implementation request, continue from decisions through tested code; for a planning-only request, stop at reviewable drafts.
2. Use the supplied plan as the ledger. Otherwise create `ledger.md` and `result.md` under a writable task workspace; prefer the repository's session workspace. Without a convention, use `~/.local/state/opencode-mission/<date>-<topic>/`. Honor a requested output path. Record absolute paths, constraints, permissions, active environment, optional profile, per-task model choices, and any permitted escalation. Read [MODEL_ROUTING.md](MODEL_ROUTING.md) before dispatch so an independent judge does not inherit the proposer’s model.
3. Make checkable tasks with dependencies and a final audit. For design, reconstruct the question tree: confirmed answers remain confirmed; unresolved questions become provisional-decision tasks. Link canonical tracker work rather than duplicating its requirements. Read [MATT.md](MATT.md) for engineering workflows and [JUDGE.md](JUDGE.md) for decision review.
4. In OpenCode only, create `.loop` at the working root as `{"mode":"afk","ledger":"<absolute path>","max_rounds":20}`, using a requested round cap. Use a session ID only when already provided by the harness; otherwise omit it for automatic plugin binding. Do not investigate the runtime to find this optional value. Preserve another session's binding. The plugin binds the selected model and variant on continuation; retain that binding on resume. Other harnesses continue in the active turn.

## Round

1. Read the ledger and current result. Choose ready independent tasks and use SKILL.md's Delegation rules to dispatch a bounded batch. Keep one writer for shared decisions and one merger for the integration branch. Check running assignments before dispatching on resume. Load each task's workflow skill.
2. Gather facts with research workers and choose provisional answers from evidence and the owner's constraints. Use [JUDGE.md](JUDGE.md) to independently challenge material decisions before dependent work relies on them. Ordinary choices already covered by an accepted decision need no repeated judgment. If no independent judge is available, preserve a useful draft but record its unvalidated status.
3. Update the deliverable after each result. Distinguish facts, owner decisions, judged provisional rulings, and unresolved alternatives. Add new questions and required implementation work before the final audit; trace each original user feature to its spec, ticket, and acceptance evidence. Keep `Needs user:` beside work requiring undelegated authority. A planning item may be done when its draft and unresolved decision are documented; implementation requiring that decision remains unticked unless its choice was explicitly delegated by the objective.
4. Inspect the result, verify citations and run the done conditions yourself after integration. On failure, send the actual failure to the worker; use at most two retries and record attempts in the ledger across resumptions. Keep a failed integration candidate separate from the last verified integration branch. Tick successful items as `- [x] <task> — evidence: <check or source> → <observed result>`, including the tested commit for code. Release dependents only after their prerequisites are integrated and verified. Keep unrelated ready work moving.
5. Print `mission AFK: <ticked>/<total> ticked; next <task>`. In OpenCode, finish or safely stop active workers in the batch before yielding for idle continuation; a round may tick several tasks. Other harnesses continue directly. Write `BLOCKED:` only when no meaningful authorized work can advance, including after exhausted retries leave all remaining paths blocked.

## Authority and exit

Use provisional, independently judged rulings in place of ordinary grilling waits. Keep the question tree, fact finding, and the distinction between a prepared answer and a human decision. Explicitly delegated low-stakes build choices may support local implementation. A planning request alone never authorizes building. Wayfinder HITL decisions remain formally open without the actual human exchange.

Secrets, destructive work, pushes, publications, messages, and protected-branch merges need existing user authorization. Local integration of worker branches is distinct from merging the target branch. A judge's approval never expands permissions. Record `Needs user:` and continue independent authorized work.

For the final audit, inspect every deliverable against **Done when**, the full plan or question tree, every Ruling, and every pending authority item. For designs, mark outputs `Draft for the user's review` and retain sources, assumptions, alternatives, and the judge's unresolved findings. For implementation, run the final acceptance checks and separate code review at a pinned commit. Remove tool-wrapper fragments and inspect the complete result. Tick the audit only when the requested result is reviewable and every branch is accounted for.

Then follow SKILL.md's Exit: remove only this run's `.loop`, notify when available, and report outputs, evidence, model routes, convergence outcomes, and remaining `Needs user:` items. A plugin cap or no-progress stop leaves partial results available for review; it does not establish completion.
